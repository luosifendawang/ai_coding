# gitplus 项目文档

> 版本：0.1.0  
> 项目名称：gitplus——本地优先的 AI 开发工作成果助手  
> 文档用途：大赛项目提交、答辩展示与部署参考

## 1. 项目概述

### 1.1 项目背景

软件研发中的有效工作信息通常分散在 Git 提交、代码 Diff、临时工作记录和个人记忆中。开发者需要反复完成三类高频工作：理解改动、撰写规范的提交信息、沉淀可追溯的工作总结。传统方式依赖人工复制、归纳和整理，存在耗时长、信息遗漏、表达不规范，以及敏感代码或凭证外泄等风险。

gitplus 面向个人开发者与小型研发团队，构建了一套“本地采集—安全分析—AI 辅助—人工确认—结构化沉淀”的闭环工具。项目以 Git 仓库为事实来源，结合本地工作日志与 SQLite 持久化记录，帮助用户完成提交信息生成、Git 工作台操作、工作日志管理、统一历史检索和智能周报整理。

### 1.2 核心目标

1. 降低开发者整理工作成果、编写提交信息和制作周报的重复劳动。
2. 让 AI 输出建立在 Git Diff、提交记录和工作日志等可追溯事实之上。
3. 在调用远程模型之前完成本地敏感信息扫描和脱敏，减少源代码泄露风险。
4. 保持用户对 Git 写操作、AI 输出和本地数据的最终控制权。
5. 通过浏览器控制台与命令行双入口，兼顾可视化操作与工程化效率。

### 1.3 适用场景

- 日常开发中的 Commit Message 生成与人工确认提交。
- 对暂存区、工作区改动进行敏感信息检查。
- 将开发、排障、测试等工作补充为结构化工作日志。
- 将 Git 提交、确认记录、工作日志统一检索、统计和导出。
- 依据指定时间范围内的真实工作记录生成可编辑的智能周报。
- 在不依赖远程服务的情况下，使用规则模式完成基础整理工作。

## 2. 功能设计

### 2.1 Git 工作台

Web 控制台提供面向仓库日常操作的 Git 工作台，主要能力包括：

- 识别当前项目是否为 Git 仓库，读取分支、文件状态与仓库修订版本。
- 分别查看已暂存、未暂存、未跟踪和冲突文件。
- 按文件执行暂存或取消暂存操作，并通过仓库修订版本防止过期页面误操作。
- 在受控大小范围内查看 Diff，避免一次性加载过大的文件内容。
- 对指定改动执行安全扫描。
- 以当前改动和用户补充上下文为依据生成提交候选文本。
- 用户可编辑主题、正文并明确确认后，才会创建本地 Git Commit。

项目不执行未经确认的 Git 写操作；所有提交动作都要求用户在界面或命令行中完成确认。

### 2.2 AI 提交信息生成

项目将模型调用封装为统一的 Provider 抽象，支持：

- `mock`：用于本地演示、离线开发和自动化测试。
- `openai-compatible`：兼容 OpenAI 风格接口的模型服务。

生成流程并非将原始代码直接交给模型，而是先读取有限范围内的 Diff 和变更上下文，完成安全检查与必要脱敏，再构造结构化请求。模型结果会经过 JSON 解析、字段校验和提交规范检查，最终产生标准、简洁、可人工修改的候选提交信息。

### 2.3 本地安全扫描与脱敏

安全模块在本地完成分析，不修改源代码，不自动删除任何内容。系统内置凭证、隐私和环境信息识别规则，可识别的高风险内容包括：

- 常见 API Key、访问令牌、Bearer Token、JWT。
- GitHub、GitLab、AWS 等服务的凭证形式。
- 明文密码、密钥字段、数据库连接字符串与 PEM 私钥。
- 私有 IPv4 地址、内网域名、本地用户目录。
- 邮箱、手机号、身份证号等个人信息。

扫描结果按 `critical`、`high`、`medium`、`low` 分级。对于高风险内容，系统默认阻止远程模型调用；对于可安全处理的信息，则使用稳定占位符进行脱敏，例如 `<API_KEY_1>`、`<EMAIL_1>`。同一内容在同一次扫描中保持一致的占位符，既保护隐私，也保留变更语义。

用户还可以通过全局配置增加自定义正则规则，或对明确的误报规则进行忽略。该机制使项目能够适配不同企业、不同技术栈和不同保密要求。

### 2.4 工作日志管理

工作日志用于补充 Git 提交之外的真实工作，例如需求分析、排障、联调、测试、评审或技术调研。每条日志可记录发生时间、类型、标题、结果、耗时、标签及关联信息。

系统支持工作日志的新增、查询、查看、编辑、复制与删除。用户可以根据时间范围、类型、标签和关键词筛选记录。结构化日志既能成为个人工作复盘材料，也能为后续周报生成提供可验证的事实来源。

### 2.5 统一工作历史

统一历史模块将多个来源汇聚到同一检索界面：

- Git 原始提交记录；
- 通过 gitplus 确认保存的提交记录；
- 手工录入的工作日志。

用户可按日期、记录类型、仓库、标签、提交类型、作者和关键词进行筛选，并查看统计信息。查询结果支持 Markdown、JSON、CSV 等格式导出，便于提交周报、制作阶段总结或归档个人研发成果。

### 2.6 智能周报助手

智能周报助手是当前 Web 端的重要功能。它通过“先选事实、再生成内容”的方式降低 AI 幻觉风险：

1. 用户选择周报日期范围。
2. 系统从统一工作历史中读取候选记录。
3. 用户勾选本次周报采用的事实来源，并可填写补充背景。
4. 系统以规则模式或 AI 模式生成包含工作成果、问题处理、风险与后续计划的周报草稿。
5. 用户可继续使用自然语言指令优化草稿，也可直接编辑 Markdown。
6. 草稿可保存、确认、重新打开、删除，并导出为 Markdown 文件。

周报记录保存来源 ID、生成器信息、版本号和状态。每次编辑都会更新版本；已确认周报再次编辑后会自动回到草稿状态，从而保证“确认”对应的是明确版本的内容。

### 2.7 配置、诊断与数据管理

项目提供完整的本地配置与维护能力：

- 系统配置页面支持查看配置来源、校验配置、预览变更、保存配置和恢复备份。
- API Key 等敏感字段存放在独立 Secret 文件中，不在前端接口、日志或普通配置预览中返回明文。
- `doctor` 命令可检查 Python、Git、仓库状态、配置、数据库和安全规则等运行环境。
- `data info` 查看数据库信息；`data backup` 创建备份；`data clear` 在明确确认后清理本地数据。

## 3. 技术架构

### 3.1 技术栈

| 类别 | 技术选型 | 作用 |
| --- | --- | --- |
| 编程语言 | Python 3.9+ | 后端、CLI、业务逻辑与工具脚本 |
| Web 框架 | FastAPI | 本地 Web API 与页面服务 |
| 模板与静态资源 | Jinja2、原生 JavaScript、CSS | 页面渲染与交互 |
| CLI 框架 | Typer、Rich | 命令解析和终端展示 |
| 数据校验 | Pydantic v2 | 配置、请求和领域模型校验 |
| ORM 与数据库 | SQLAlchemy、SQLite | 本地结构化数据存储与迁移 |
| HTTP 客户端 | HTTPX | OpenAI 兼容模型服务调用 |
| 配置格式 | YAML | 全局配置与 Secret 管理 |
| 测试工具 | Pytest | 单元、集成、端到端及性能测试 |

### 3.2 分层结构

```text
用户（CLI / 浏览器）
        │
        ▼
交互层：Typer CLI、FastAPI 路由、Jinja2 页面
        │
        ▼
应用服务层：提交、工作日志、历史、周报、配置、诊断服务
        │
        ├──────────────► AI 层：Provider 抽象、请求构建、响应解析
        ├──────────────► 安全层：扫描、分级、脱敏、远程调用拦截
        ├──────────────► Git 层：仓库状态、Diff、暂存、提交、日志读取
        └──────────────► 存储层：SQLAlchemy Repository、Unit of Work、SQLite
```

该结构将界面交互、业务规则、外部 Git 调用、模型调用与数据库访问解耦。服务层只依赖明确的领域模型和接口，因此既方便单元测试，也方便将来替换模型服务或扩展数据来源。

### 3.3 Web 安全设计

Web 服务固定面向本机使用，默认监听 `127.0.0.1:8765`。系统通过一次性本地访问令牌建立 Session，并使用 CSRF 校验保护有状态请求。配置修改采用版本修订号机制：当配置文件在页面打开后被其他终端或进程修改时，保存会返回冲突，而不是静默覆盖用户内容。

### 3.4 数据模型与持久化

项目使用 SQLite 作为本地优先的数据存储。核心数据包括：

- 仓库记录：保存本地仓库身份信息。
- 提交记录：保存已确认的提交生成结果及必要上下文。
- 工作日志：保存用户录入的结构化工作信息。
- 周报记录：保存日期范围、标题、Markdown、来源、生成方式、版本和状态。
- 操作审计：保存关键 Web 操作的结果摘要。
- 数据库迁移记录：保证版本升级过程可追踪。

多表写入使用 Unit of Work 协调事务，减少部分成功、部分失败造成的数据不一致。数据库文件、报告目录和配置目录由平台目录规范统一管理，适合个人与小团队在本机长期使用。

## 4. 关键业务流程

### 4.1 安全的 AI Commit 流程

```text
读取 Git 状态与 Diff
        ↓
本地敏感信息扫描
        ↓
高风险？──是──► 阻止远程模型调用并展示风险
        │否
        ▼
脱敏、截断并构造结构化 AI 请求
        ↓
模型生成候选提交信息
        ↓
解析与规则校验
        ↓
用户编辑、确认
        ↓
创建本地 Commit 并保存记录
```

### 4.2 智能周报流程

```text
选择日期范围 → 查询统一历史 → 勾选事实来源
      ↓
规则或 AI 生成周报草稿 → 用户优化/编辑 → 保存
      ↓
确认正式版本 → 导出 Markdown → 本地归档
```

### 4.3 配置保存流程

```text
加载默认配置与用户配置
        ↓
页面编辑并执行 Pydantic 校验
        ↓
展示变更预览
        ↓
确认保存
        ↓
创建备份、原子写入、更新修订版本
```

## 5. 命令行使用说明

常用命令示例如下：

```bash
# 初始化或检查当前仓库环境
gitplus init
gitplus doctor

# 扫描暂存区或工作区的敏感信息
gitplus check --staged
gitplus check --unstaged

# 生成提交信息并执行确认提交
gitplus commit --provider mock

# 管理工作日志
gitplus worklog add --yes --type development --title "完成核心模块"
gitplus worklog list

# 查询历史
gitplus history list
gitplus history show <record-id>

# 启动本地 Web 控制台
gitplus web
gitplus web --no-open

# 数据维护
gitplus data info
gitplus data backup
```

具体选项可通过 `gitplus --help` 或子命令后的 `--help` 查看。

## 6. 安装与部署

### 6.1 环境要求

- Python 3.9 或更高版本。
- Git 已安装且可通过 `git --version` 正常访问。
- Windows、macOS 或 Linux 本地环境。

### 6.2 开发环境安装

```bash
git clone <repository-url>
cd gitplus
python -m venv .venv

# Windows PowerShell
.\.venv\Scripts\Activate.ps1

pip install -e ".[dev]"
gitplus --version
gitplus doctor
```

### 6.3 配置模型服务

可在配置文件中填写 OpenAI 兼容服务地址、模型名称和环境变量名称；密钥应配置在环境变量或本地 Secret 文件中。例如：

```yaml
ai:
  provider: openai-compatible
  model: your-model-name
  base_url: https://api.example.com/v1
  api_key_env: GITPLUS_API_KEY
```

也可选择 `mock` Provider 进行离线演示和测试。

### 6.4 启动 Web 控制台

```bash
gitplus web
```

默认端口为 `8765`。如需指定端口或禁止自动打开浏览器：

```bash
gitplus web --port 8766 --no-open
```

## 7. 测试与质量保障

项目采用 Pytest 组织测试，覆盖单元测试、集成测试、端到端测试与性能检查。建议执行：

```bash
pytest
pytest tests/e2e tests/performance
python scripts/check_secrets.py
python -m build
```

测试重点包括：

- 配置模型与字段合法性校验。
- Git 状态读取、Diff 安全边界和提交确认流程。
- 敏感信息规则、脱敏占位符与远程调用阻断。
- AI 响应解析、失败降级和错误信息脱敏。
- 工作日志、历史查询、导出和数据库事务。
- 周报的来源选择、草稿保存、版本更新、确认状态与导出。
- Web 的本地会话、CSRF、防冲突配置保存与 API 访问控制。

## 8. 项目创新点

### 8.1 面向开发过程的“事实优先”AI 辅助

项目不是简单的文本生成器，而是将 Git Diff、提交记录和工作日志作为事实来源。周报生成要求用户先选择依据，提交信息生成则建立在实际变更与安全扫描结果上，从流程上降低无依据内容进入成果文档的概率。

### 8.2 本地优先的安全边界

在模型调用之前进行本地扫描、风险分级与脱敏，避免将原始敏感片段直接发送到远程服务。对于高风险信息，系统默认阻断远程调用，并将最终决策保留给用户。

### 8.3 人机协同而非自动替代

系统强调“生成建议—用户编辑—明确确认”的协作模式。无论是 Git 提交还是周报确认，AI 都不替代开发者做最终业务判断，适合对工程可控性与成果真实性有要求的场景。

### 8.4 双入口与统一数据闭环

CLI 适合开发者的终端工作流，Web 控制台适合可视化查看与编辑；两者共享本地数据模型。Git 改动、工作日志、历史查询和周报沉淀形成从日常开发到阶段总结的完整闭环。

## 9. 局限性与后续规划

当前版本定位于本地开发辅助工具，SQLite 更适用于个人或小团队使用；AI 输出仍需要人工审阅；安全规则无法保证覆盖所有潜在敏感信息；系统暂不提供远程仓库同步、多人协同、IDE 插件和复杂项目管理能力。

后续可从以下方向迭代：

1. 引入更丰富的本地模型与离线推理适配能力。
2. 增强周报模板、统计图表和多周期报告能力。
3. 扩展测试报告、Issue、代码审查等事实来源。
4. 支持可配置的团队级规则包和合规审计策略。
5. 提供 IDE 扩展与更精细的 Git 工作流集成。

## 10. 结语

gitplus 将 Git、AI、安全扫描、结构化工作记录和周报整理整合为一套本地优先的开发辅助系统。项目关注的不只是“更快生成文本”，而是让开发成果具备可追溯性、安全性与可复核性。通过明确的人机协作边界和模块化架构，gitplus 能够为日常研发效率提升、个人成果沉淀和小型团队工程实践提供可靠支撑。
