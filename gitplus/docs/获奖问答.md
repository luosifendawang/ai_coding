# 个人赛三等奖 · 获奖问答

> 作品：gitplus —— 本地优先的 AI 开发工作成果助手

## 1. 作品名字

**gitplus —— 本地优先的 AI 开发工作成果助手**

## 2. 作品介绍 + 解决什么问题

gitplus 是一款面向个人开发者与小型研发团队的本地优先工具。它以 Git 仓库为事实来源，从 Git Diff、提交记录、手工工作日志和本地结构化数据（SQLite）中提取真实信息，构建了一条"**本地采集 → 安全分析 → AI 辅助 → 人工确认 → 结构化沉淀**"的完整闭环，提供 Git 工作台、AI 提交信息生成、本地敏感信息扫描与脱敏、工作日志管理、统一历史检索和智能周报助手等能力，同时支持命令行和本地 Web 控制台双入口。

它主要解决三类高频痛点：

1. **重复劳动多**：开发者每天都要理解改动、编写规范的提交信息、阶段性整理工作总结和周报，传统方式靠人工复制、归纳，耗时长、容易遗漏、表达不规范。
2. **AI 输出不可信**：直接让大模型"凭空"写总结容易产生幻觉。gitplus 让 AI 的输出严格建立在用户勾选的真实事实来源（Diff、提交、工作日志）之上，并且结果必须经过人工审阅确认，绝不在未确认的情况下执行 `git add / commit / push`。
3. **代码安全有顾虑**：把源码交给远程模型存在凭证、密钥、内网信息和个人隐私泄露的风险。gitplus 在调用远程模型之前先在本地完成敏感信息扫描，按 critical/high/medium/low 分级，高风险内容默认阻断远程调用，可处理内容用稳定占位符脱敏，从机制上守住安全底线。

## 3. 获奖感受 + 最大收获

作为一名刚进入公司的应届生，能在应届 AI 大赛中拿到个人赛三等奖，对我既是惊喜也是鼓励。惊喜的是，从入职到现在其实时间并不长，我是在一边适应工作、一边啃陌生技术栈的情况下挤出时间完成这个项目的；鼓励的是，评委认可的不是"炫技的 Demo"，而是一个有明确边界、有安全设计、真正考虑落地可用性的完整作品。对一个新人来说，这份认可很大程度上缓解了我"经验不够、能力不足"的焦虑——它证明了在 AI 时代，新人也可以借助 AI 快速补齐执行层的差距，做出有分量的东西。

而最大的收获，是我对"AI 时代工程师该把力气花在哪"这个问题有了切身的重新认识：

- **编码能力的权重在下降，产品思维和架构能力在上升**。以前在学校做项目，比拼的更多是谁代码写得好、算法实现得漂亮；做 gitplus 时我发现，具体代码 AI 可以帮我快速生成，真正决定作品质量的，是我有没有想清楚要解决什么问题、功能边界在哪里、模块如何分层解耦、安全机制如何设计。我把大量时间花在了需求取舍和架构设计上（交互层 / 服务层 / AI 层 / 安全层 / Git 层 / 存储层的划分），而不是逐行敲代码——这反而让项目完成得又快又稳。
- **经验和认知决定你使用 AI 的上限**。同样是大模型，有人只能问出"帮我写个函数"，有人能让它成为可靠的结对工程师。差距不在工具，而在提问的人有没有清晰的上下文意识、有没有能力判断 AI 输出的对错。做这个项目让我系统理解了 Provider 抽象、结构化 Prompt、事实来源约束、输出校验这些"让 AI 可信"的工程手段；而在日常里，我用 AI 理解 C++ 代码、Android 源码、音频设备树和 audio bring up 问题时也深切体会到：AI 给的答案能不能被采信，取决于我自己的底层认知够不够——**AI 放大的是你的认知，认知不足时它放大的是错误**。
- **学会了做减法，这是新人最容易缺失的一课**。比赛过程中我主动砍掉了一些"看起来炫"但偏离核心价值的功能，把精力集中在安全、可控、可验证上。想清楚"不做什么"，和想清楚"做什么"同样重要。

## 4. 比赛对你的意义

我的岗位是 Java framework 开发，偏底层和支撑性；最近日常工作中大量借助 AI 来帮我理解 C++ 项目代码、Android 系统源码、音频设备树和 audio bring up 这类陌生领域的"硬骨头"。这次比赛对我的意义在于：

- **完成了从"AI 的使用者"到"AI 工具的作者"的身份转变**。平时我是用 AI 的人——让它帮我读源码、解释设备树、梳理 bring up 流程；这次比赛逼着我站到另一边，去思考一个 AI 工具应该怎么设计才安全、可信、可控。这段经历让我再用 AI 时，对它的能力边界和工程约束有了更本质的理解。
- **验证了"用 AI 造工具解决自己的问题"这条路对新人尤其可行**。作为应届生，我接触的业务领域（framework、音频、系统源码）都很陌生，靠传统方式积累要花很长时间；而借助 AI，我可以快速理解陌生领域，并把理解沉淀成结构化的工作日志和历史记录——gitplus 的工作日志、统一历史功能，本身就可以服务于这种跨技术栈、强学习属性的工作节奏。比赛让我意识到，新人不必等"经验够了"才动手，可以把 AI 编织进自己的学习和工作流，加速成长。
- **给了我在新环境中建立技术自信的支点**。入职初期面对完全陌生的技术栈，难免有畏难情绪。独立从零到一交付一个有测试、有文档、有安全设计的产品级项目并获奖，让我确认了自己具备端到端解决问题的能力——这种自信对一个新人的长期成长非常重要。

## 5. 觉得 AI 对你未来的工作意味着什么，怎么理解 AI

**AI 对我未来工作意味着一次工作方式的结构性升级，而不是一个简单的"提效插件"。它会重新定义"什么样的工程师更有价值"。**

结合我入职以来的真实体感，我看到三个层面的变化：

1. **执行层：AI 是放大器，也是新人的加速器**。读 C++ 项目代码、查 Android 系统源码、分析音频设备树、排查 bring up 问题时，AI 可以快速定位关键路径、解释陌生 API、梳理调用链，把"读懂代码"的时间大幅压缩。对应届生来说这尤其关键——它部分抹平了新人最缺的"经验存量"，让我能更快进入陌生领域并产出价值。
2. **能力层：重心从"会写代码"转向"会定义问题和判断答案"**。当编码本身可以被 AI 加速，工程师的稀缺能力就变成了：产品思维（做对的事）、架构能力（把事做对的结构）、领域认知（判断 AI 输出的对错）。未来衡量一个工程师，不再只看他实现得多快，而是看他给 AI 的上下文有多准、对 AI 产出的把关有多严、以及他能不能把模糊需求转化为 AI 可执行的清晰任务。
3. **风险层：AI 是需要工程约束的合作者**。大模型有幻觉、有数据泄露风险，直接依赖裸模型是不可接受的。应该像对待一个"聪明但不完全可靠的实习生"一样对待 AI——给它明确的边界（本地扫描、脱敏、阻断机制）、给它可追溯的事实来源、要求它的输出必须经过人工确认。这正是 gitplus 的设计信念：**AI 负责生成，人负责确认，事实负责兜底**。

我对 AI 的理解可以概括为一句话：**AI 不会取代工程师，但会用 AI、并且知道 AI 边界的工程师，会取代不会的；而对新人来说，AI 时代最大的机会是——认知成长的速度可以远快于从前，但前提是你始终知道自己为什么采信 AI 的每一个答案。** AI 的本质是一个概率性的知识与推理引擎，它输出的价值上限由使用者的认知决定。所以越是 AI 时代，我越要坚持深入底层——framework、系统源码、bring up 这些"硬知识"恰恰是我判断 AI 对错的底气所在。gitplus 是我作为新人探索"人与 AI 如何安全、可信地协作"的第一份答卷，未来我会继续沿着这条路走下去。
