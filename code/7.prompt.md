# 一、本阶段目标

本阶段实现 GitPulse 的飞书通知闭环：

```text
读取已确认周报
    ↓
验证周报状态
    ↓
重新执行敏感信息扫描
    ↓
生成飞书文本或消息卡片
    ↓
检查消息大小和结构
    ↓
计算内容指纹
    ↓
检查是否重复发送
    ↓
展示发送预览
    ↓
用户明确确认
    ↓
生成飞书机器人签名
    ↓
调用飞书 Webhook
    ↓
解析飞书响应
    ↓
保存发送记录
    ↓
更新周报发送状态
```

# 五、设计原则

必须遵循：

1. 只有用户确认后的正式周报可以发送。
2. Draft 周报不得发送。
3. 存在待确认内容的周报不得发送。
4. 来源覆盖率不足 100% 的周报不得发送。
5. 包含 High 或 Critical 敏感信息的内容不得发送。
6. 默认发送前必须展示预览。
7. 默认必须由用户明确确认。
8. Webhook 和 Secret 只能从环境变量读取。
9. Webhook 不得写入 `.gitpulse.yml`。
10. Secret 不得写入数据库。
11. Webhook 不得出现在日志中。
12. 发送失败不得错误标记为成功。
13. 同一内容不得在无确认的情况下重复发送。
14. HTTP 请求必须设置超时。
15. 外部错误必须转换为业务异常。
16. 飞书错误不得破坏本地周报。
17. 通知记录必须可审计。
18. 通知模块不得修改 Git 仓库状态。
19. 自定义机器人只作为消息发送出口。
20. 不将飞书发送成功视为周报事实正确性的证明。

# 六、飞书配置

完善 `.gitpulse.yml`：

```yaml
feishu:
  enabled: false
  webhook_env: GITPULSE_FEISHU_WEBHOOK
  secret_env: GITPULSE_FEISHU_SECRET
  message_type: interactive
  require_confirmation: true
  allow_duplicate_send: false
  include_sources: false
  include_generator_info: false
  include_report_id: true
  include_generated_at: true
  mention_all: false
  mention_open_ids: []
  max_json_bytes: 28000
  request_timeout_seconds: 10
  max_retries: 2
  retry_backoff_seconds: 0.5
  duplicate_window_hours: 168
  test_message_enabled: true
```

说明：

* `max_json_bytes` 使用保守值，不要直接把平台极限写死在业务逻辑中
* 实际请求前必须计算 UTF-8 JSON 字节数
* `duplicate_window_hours=168` 表示默认检查最近七天
* 所有限制应允许通过配置调整
* 配置调整仍需满足合理边界校验

建议配置模型：

```python
from typing import Literal

from pydantic import BaseModel, Field, field_validator


class FeishuConfig(BaseModel):
    enabled: bool = False
    webhook_env: str = "GITPULSE_FEISHU_WEBHOOK"
    secret_env: str = "GITPULSE_FEISHU_SECRET"

    message_type: Literal[
        "text",
        "interactive",
    ] = "interactive"

    require_confirmation: bool = True
    allow_duplicate_send: bool = False
    include_sources: bool = False
    include_generator_info: bool = False
    include_report_id: bool = True
    include_generated_at: bool = True

    mention_all: bool = False
    mention_open_ids: list[str] = Field(default_factory=list)

    max_json_bytes: int = 28000
    request_timeout_seconds: float = 10.0
    max_retries: int = 2
    retry_backoff_seconds: float = 0.5
    duplicate_window_hours: int = 168
    test_message_enabled: bool = True
```

配置校验要求：

* `webhook_env` 不得为空
* `secret_env` 不得为空
* `max_json_bytes` 必须大于 1000
* `request_timeout_seconds` 必须大于 0
* `max_retries` 范围建议为 0 至 5
* `retry_backoff_seconds` 不得小于 0
* `duplicate_window_hours` 必须大于 0
* `mention_open_ids` 去重
* Open ID 不符合基本格式时提示配置错误
* `mention_all=true` 时必须再次由用户确认
* 默认 `mention_all=false`
* 不允许在配置中出现 `webhook` 或 `secret` 明文值
* 检测到明文 Webhook 时应拒绝加载并提示迁移到环境变量

# 七、环境变量

飞书配置只允许从以下环境变量读取真实凭证：

```text
GITPULSE_FEISHU_WEBHOOK
GITPULSE_FEISHU_SECRET
```

读取方式：

```python
webhook = os.getenv(config.webhook_env)
secret = os.getenv(config.secret_env)
```

规则：

## Webhook 缺失

```text
未配置飞书机器人 Webhook。

请设置环境变量：

GITPULSE_FEISHU_WEBHOOK
```

## Secret 缺失

如果机器人没有启用签名校验：

* Secret 可以为空
* 请求中不包含 `timestamp` 和 `sign`

如果机器人启用了签名校验但本地未配置 Secret：

* 请求会失败
* GitPulse 应在发送前提示用户检查配置
* 不要在错误消息中显示 Secret

可以增加配置：

```yaml
feishu:
  signature_required: true
```

建议模型：

```python
signature_required: bool = True
```

当：

```text
signature_required=true
secret 缺失
```

必须在 HTTP 请求前失败。

# 八、Webhook 安全校验

Webhook 是敏感凭证。

读取后需要进行基础校验：

1. 必须为 HTTPS。
2. 必须使用允许的飞书域名。
3. 禁止任意用户 URL。
4. 禁止 localhost。
5. 禁止内网 IP。
6. 禁止 URL 中包含用户名和密码。
7. 禁止 URL Fragment。
8. 不在错误中输出完整 URL。
9. 不在日志中输出 Query 参数。
10. 不把 Webhook 返回给 CLI JSON。

建议：

```python
class FeishuWebhookValidator:
    def validate(self, webhook: str) -> None:
        ...

    def mask(self, webhook: str) -> str:
        ...
```

脱敏形式：

```text
https://open.feishu.cn/open-apis/bot/v2/hook/****abcd
```

实际允许域名应集中配置，并根据官方域名更新。

不要使用简单的：

```python
"feishu" in webhook
```

进行安全判断。

需要正确解析 URL Host。

# 九、飞书签名生成器

实现：

```text
src/gitpulse/integrations/feishu_signer.py
```

建议接口：

```python
from dataclasses import dataclass
from datetime import datetime
from typing import Protocol


class Clock(Protocol):
    def now_timestamp(self) -> int:
        ...


@dataclass(frozen=True)
class FeishuSignature:
    timestamp: str
    sign: str


class FeishuSigner:
    def __init__(
        self,
        secret: str,
        clock: Clock,
    ) -> None:
        ...

    def generate(self) -> FeishuSignature:
        ...
```

要求：

1. 使用秒级 Unix 时间戳。
2. 使用飞书官方文档规定的签名算法。
3. 使用标准库 `hmac`、`hashlib` 和 `base64`。
4. 不手写自定义加密算法。
5. Secret 不得打印。
6. 签名不得长期缓存。
7. 每次发送重新生成时间戳和签名。
8. Clock 必须可注入。
9. 测试必须使用固定时间。
10. 使用官方示例或可验证测试向量编写单元测试。
11. 签名函数不得访问环境变量。
12. 签名函数只接收已经加载的 Secret。
13. 空 Secret 时应抛出配置错误。
14. 编码统一使用 UTF-8。
15. 返回值只包含 `timestamp` 和 `sign`。

不要在日志中输出完整 `sign`。

调试日志最多记录：

```text
signature generated timestamp=...
```

# 十二、HTTP 请求要求

使用：

```text
httpx
```

请求：

```python
response = client.post(
    webhook,
    json=payload,
    headers={
        "Content-Type": "application/json; charset=utf-8",
    },
    timeout=config.request_timeout_seconds,
)
```

要求：

1. 只允许 POST。
2. 使用 HTTPS。
3. 声明 UTF-8。
4. 设置连接和读取超时。
5. 不自动跟随跨域重定向。
6. 如果发生重定向，应视为配置异常或网络风险。
7. 不将 Webhook 写入异常。
8. 不将完整请求体写入日志。
9. 不将完整响应写入普通日志。
10. 设置明确 User-Agent，例如：

```text
GitPulse/<version>
```

11. 不使用 `verify=False`。
12. 不关闭 TLS 证书校验。
13. 不使用 `shell=True`。
14. 客户端需要支持依赖注入，方便 Mock。

# 十三、重试策略

允许重试：

* 连接错误
* 连接超时
* 读取超时
* HTTP 429
* HTTP 500
* HTTP 502
* HTTP 503
* HTTP 504

不自动重试：

* HTTP 400
* HTTP 401
* HTTP 403
* Webhook 不合法
* 签名配置错误
* 飞书明确返回请求参数错误
* 消息结构错误
* 消息过长
* 用户取消
* 重复发送被阻止

退避策略：

```text
第一次重试：0.5 秒
第二次重试：1 秒
```

推荐指数退避：

```python
delay = retry_backoff_seconds * (2 ** attempt)
```

要求：

* 最大重试次数可配置
* 测试不真实等待
* 注入 Sleeper
* 保存最终尝试次数
* 每次重试使用新时间戳和新签名
* 不复用过期签名
* 不对成功请求重复发送
* 网络返回不确定时应谨慎处理重复问题

对于以下情况：

```text
请求已经发出，但客户端读取响应超时
```

不能确定飞书是否已经收到消息。

处理方式：

* Notification 状态标记为 `unknown`
* 不自动立即无限重试
* 提示用户检查飞书群消息
* 用户再次发送时触发重复发送确认
* 保留本次尝试记录

# 十四、飞书响应模型

定义：

```python
from typing import Any

from pydantic import BaseModel, Field


class FeishuSendResponse(BaseModel):
    success: bool
    http_status: int | None = None
    code: int | str | None = None
    message: str | None = None
    request_id: str | None = None
    raw_metadata: dict[str, Any] = Field(default_factory=dict)
```

解析规则：

1. HTTP 2xx 不一定表示业务成功。
2. 必须检查响应 JSON 中的业务码。
3. 业务成功码应集中定义。
4. 不要假设所有错误结构完全一致。
5. 非 JSON 响应视为协议错误。
6. HTML 响应视为网络或网关错误。
7. 空响应视为协议错误。
8. 解析失败不得标记成功。
9. `raw_metadata` 不保存敏感字段。
10. 响应中的 Request ID 可以安全保存。
11. 响应错误消息需要限制长度。
12. 不把整个响应原文写入数据库。

第六阶段状态：

第七阶段增加：

* 多渠道发送
* 多次发送
* 导出和发送组合
* 发送失败后的状态恢复

```text
WeeklyReport.status = confirmed
```

# 三十、发送前安全检查

NotificationService 必须在发送前重新检查最终 Payload。

扫描对象：

* 文本消息正文
* 卡片标题
* 卡片 Markdown 内容
* Source 展示
* 用户编辑内容
* @ 配置中的文本字段

处理规则：

## Critical 或 High

* 阻止发送
* 不调用 FeishuClient
* 保存 `failed` 或 `cancelled` 记录需要谨慎
* 推荐创建 `failed` 记录，error_type 为 `security_block`
* 提示用户修改周报后重新确认

## Medium

* 展示脱敏预览
* 用户确认后发送脱敏结果
* 不发送原始内容

## Low

* 根据现有 SecurityConfig 处理

必须验证：

```text
FeishuClient 接收到的 Payload 已经是最终脱敏版本
```

不得出现：

```text
先发送，再扫描
```

# 三十三、Notification Service

实现：

```text
src/gitpulse/services/notification_service.py
```

建议接口：

```python
class NotificationService:
    def prepare_weekly(
        self,
        report_id: str,
        *,
        message_type: str | None = None,
    ) -> NotificationPayload:
        ...

    def preview_weekly(
        self,
        report_id: str,
        *,
        message_type: str | None = None,
    ) -> NotificationPreview:
        ...

    def send_weekly(
        self,
        report_id: str,
        *,
        confirmed: bool,
        force: bool = False,
        message_type: str | None = None,
    ) -> NotificationRecord:
        ...

    def retry(
        self,
        notification_id: str,
        *,
        confirmed: bool,
    ) -> NotificationRecord:
        ...

    def test_connection(
        self,
        *,
        confirmed: bool,
    ) -> NotificationRecord:
        ...
```

处理顺序必须为：

```text
查询周报
    ↓
校验发送资格
    ↓
构造文本或卡片
    ↓
限制内容大小
    ↓
重新执行安全扫描
    ↓
生成最终 Payload
    ↓
计算内容哈希
    ↓
重复发送检查
    ↓
创建 Pending 记录
    ↓
展示预览
    ↓
用户确认
    ↓
状态改为 Confirmed
    ↓
状态改为 Sending
    ↓
调用 FeishuClient
    ↓
解析响应
    ↓
更新 Sent、Failed 或 Unknown
```

要求：

* 不在数据库事务中长期等待 HTTP 请求
* 先提交 `sending` 状态，再调用 HTTP
* HTTP 完成后开启新事务更新结果
* 防止进程中断后一直停留在 `sending`
* 可在后续查询中识别过期 `sending`
* 过期 `sending` 可标记为 `unknown`
* 不把网络调用放在持有写锁的数据库事务里


# 三十七、发送周报命令

```bash
gitpulse notify weekly <report-id>
```

支持：

```bash
gitpulse notify weekly <report-id> --type interactive

gitpulse notify weekly <report-id> --yes
gitpulse notify weekly <report-id> --force

```

规则：

* `--preview` 只预览，不发送
* `--yes` 明确确认发送
* `--force` 允许重复发送，但仍需 `--yes`
* `--mention-all` 需要额外确认
* `--json` 输出执行结果 JSON
* JSON 模式不得输出 Secret 或 Webhook
* 非交互环境未提供 `--yes` 时不得发送
* `--include-sources` 只影响本次消息，不修改周报
* `--type` 只影响本次发送，不修改全局配置

# 四十一、失败重试

```bash
gitpulse notify retry <notification-id>
```

只允许重试：

```text
failed
unknown
```

对于 `unknown`：

* 必须提示可能已经发送
* 默认不重试
* 用户需要额外确认
* 建议使用 `--force`

对于 `failed`：

* 重新读取当前报告
* 重新构造消息
* 重新执行安全扫描
* 重新检查重复
* 重新生成签名
* 创建新的 NotificationRecord
* 在新记录中关联：

```text
retry_of = notification_xxx
```

不要直接复用旧 Payload，原因：

* 周报可能已经更新
* 配置可能已经变化
* 安全规则可能已经变化
* 签名必须重新生成
