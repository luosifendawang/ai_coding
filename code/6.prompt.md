# 一、本阶段目标

本阶段实现 GitPulse 的开发周报完整生成流程。

完整数据链路：

```text
确定周报日期范围
    ↓
读取当前用户 Git Commit
    ↓
读取 GitPulse Commit 结构化记录
    ↓
读取手动 Worklog
    ↓
读取可选未提交变更
    ↓
读取用户补充风险和下周计划
    ↓
规范化和去重数据
    ↓
识别相关工作主题
    ↓
合并同一目标下的多个 Commit
    ↓
生成结构化周报
    ↓
校验每条内容的事实来源
    ↓
计算可信度
    ↓
将中低可信内容交给用户确认
    ↓
生成可编辑 Markdown 草稿
    ↓
用户确认
    ↓
保存正式周报
    ↓
导出 Markdown、纯文本或 JSON
```

本阶段必须完成：

1. 周报日期范围计算
2. 当前用户 Commit 筛选
3. 多 Git 邮箱支持
4. Commit、CommitRecord 和 Worklog 数据合并
5. 数据标准化与重复记录识别
6. 工作主题聚合
7. AI 周报生成
8. 规则降级周报生成
9. 周报结构化数据模型
10. 事实来源绑定
11. 可信度控制
12. 中低可信内容确认
13. 周报事实校验
14. Markdown 周报生成
15. 周报编辑与确认
16. 周报数据库保存
17. Markdown、纯文本和 JSON 导出
18. `gitpulse weekly` 命令
19. 单元测试和集成测试

本阶段暂不实现：

* 飞书机器人发送
* 企业微信发送

* PDF 导出

# 四、周报设计原则

必须遵循：

1. 所有正式周报内容必须具有来源。
2. 来源必须是 Commit、CommitRecord、Worklog、未提交变更或用户确认说明。
3. 不得编造工作成果。
4. 不得编造测试结果。
5. 不得编造性能提升。
6. 不得编造业务收益。
7. 不得根据代码行数判断贡献。
8. 不得根据 Commit 数量判断重要性。
9. 不得逐条复制 Commit Message 作为最终周报。
10. 同一目标下的多个 Commit 应尽量合并。
11. 不相关的工作不得强行合并。
12. 中可信内容必须由用户确认。
13. 低可信内容默认不进入正式周报。
14. 下周计划不能完全由 AI 自行编造。
15. 风险内容不能被自动改写为已解决。
16. AI 只负责归纳，不负责评价开发人员绩效。
17. 最终周报必须可以由用户编辑。
18. 飞书发送尚未实现，本阶段只保存和导出正式周报。
19. 原始完整 Diff 默认不进入周报生成 Prompt。
20. 发送给模型的数据必须经过安全扫描和脱敏。

建议模型：

```python
from typing import Literal
from pydantic import BaseModel, Field


class WeeklyConfig(BaseModel):
    week_start: Literal[
        "monday",
        "sunday",
    ] = "monday"

    timezone: str = "Asia/Shanghai"
    include_uncommitted: bool = False
    include_merge_commits: bool = False
    include_commit_sources: bool = True
    include_worklog_sources: bool = True
    exclude_low_confidence: bool = True
    require_medium_confirmation: bool = True
    group_by_repository: bool = False
    max_commits: int = 200
    max_worklogs: int = 200
    max_topics: int = 20
    max_items_per_topic: int = 10
    output_language: str = "zh-CN"
    output_style: Literal[
        "developer",
        "summary",
    ] = "developer"
    export_formats: list[str] = Field(
        default_factory=lambda: [
            "markdown",
            "text",
            "json",
        ]
    )
```

配置校验要求：

* 时区名称必须合法
* `max_commits` 必须大于 0
* `max_worklogs` 必须大于 0
* `max_topics` 必须大于 0
* `max_items_per_topic` 必须大于 0
* 导出格式只能使用受支持值
* 默认星期一作为自然周开始
* 用户显式指定日期时忽略自然周计算
* 日期范围的结束时间不得早于开始时间

```python
class WeeklyDateRangeResolver:
```

要求：

默认范围：

```text
本周周一 00:00:00
至当前时间
```

如果 `week_start=sunday`，则从星期日开始。

## 上一周

范围：

```text
上一自然周开始日 00:00:00
至上一自然周结束日 23:59:59.999999
```

命令：


* 使用 timezone-aware datetime
* 不使用无时区 datetime
* 正确处理跨月
* 正确处理跨年
* 正确处理夏令时地区
* 测试中注入固定当前时间
* 不直接依赖测试执行当天日期
* 日期范围显示使用自然日期
* 数据库查询应使用 UTC 时间或统一转换策略

# 七、周报数据来源

周报默认使用：

1. 当前用户在日期范围内的 Git Commit
2. GitPulse 已确认 CommitRecord
3. 手动 Worklog
4. 用户选择的未提交变更
5. 用户补充说明
6. 用户确认的风险
7. 用户输入的下周计划

不使用：

* 未确认 CommitRecord
* 已删除 Worklog
* 低可信且未确认内容
* 被安全扫描阻断的原始内容
* 未经用户确认的 AI 推断
* 与当前日期范围无关的历史数据

# 八、作者识别

默认从以下位置读取作者邮箱：

```bash
git config user.email
```

配置允许多个邮箱：

```yaml
user:
  git_emails:
    - user@example.com
    - user@company.com
```

作者筛选规则：

1. 优先使用配置中的 `git_emails`。
2. 配置为空时使用当前仓库 Git 用户邮箱。
3. 邮箱比较默认忽略大小写。
4. 去除首尾空格。
5. 多个邮箱应进行去重。
6. 不根据作者姓名筛选，因为姓名可能重复。
7. 如果无法确定作者邮箱，应提示用户。
8. 不得默认读取所有人的 Commit 生成个人周报，除非用户显式允许。

错误提示：

```text
未配置 Git 用户邮箱。

GitPulse 无法准确识别属于你的提交。

请执行：

git config user.email "you@example.com"

或在 .gitpulse.yml 中配置：

user:
  git_emails:
    - you@example.com
```

可以提供参数：

```bash
gitpulse weekly --author user@example.com
```

但不得把临时作者参数永久写入配置。

# 十一、Commit 与 CommitRecord 关联

同一个 Git Commit 可能同时存在：

* Git Log Commit
* GitPulse CommitRecord
* Risk 记录
* 用户最终选择的 Commit Message

需要进行关联。

关联优先级：

1. `commit_hash` 完全匹配
2. 同一仓库、同一 Subject、接近时间
3. 同一仓库、文件列表高度重合
4. 无法可靠关联时保持独立，并标记待确认

不要因为 Subject 相同就直接合并。

建议模型：

```python
class CommitAssociation(BaseModel):
    commit_hash: str
    commit_record_ids: list[str]
    confidence: str
    reason: str
```

规则：

* Hash 完全匹配：high
* Subject、文件和时间均接近：medium
* 仅 Subject 相同：low，不自动关联
* 一个 Record 不应自动关联多个不同 Commit
* 一个 Commit 可以关联一次生成记录和风险记录
* 关联行为必须可追踪

# 十三、重复数据识别

实现：

```text
src/gitpulse/weekly/deduplicator.py
```

需要处理：

## 1. Git Commit 与 CommitRecord 重复

如果 Hash 完全一致，合并来源。

## 2. 多个 Commit 属于同一工作目标

例如：

```text
fix(usb): 增加设备断开状态检查
fix(usb): 清理失效连接对象
test(usb): 补充设备连续插拔测试
```

这些可以聚合为：

```text
USB 设备异常断开处理
```

但不能丢失来源。

## 3. Worklog 与 Commit 内容重复

例如 Worklog 记录：

```text
完成 USB 断开资源释放修复
```

如果已经由 Commit 证明：

* Worklog 可以作为补充来源
* 不应重复生成两条成果
* 如果 Worklog 提供额外验证结果，应保留额外部分

## 4. 相同文本重复

完全相同的标题和结果应合并，但保留全部来源。

## 5. 相似但不相同

不要只使用模糊字符串相似度自动删除。

需要结合：

* 仓库
* 模块
* 时间
* Type
* 文件
* 来源
* 用户说明

建议输出：

```python
class DeduplicationResult(BaseModel):
    items: list[NormalizedWeeklyItem]
    merged_groups: list[DeduplicationGroup]
    ambiguous_groups: list[DeduplicationGroup]
```

所有自动合并必须保留合并原因。

# 十四、工作主题聚合

实现：

```text
src/gitpulse/weekly/topic_clusterer.py
```

聚合依据：

1. Scope
2. 文件路径所属模块
3. Commit Type
4. Subject 语义
5. Commit 时间接近程度
6. 用户 Worklog 标签
7. CommitRecord Summary
8. 用户补充说明
9. 同一问题处理链路
10. 测试与对应功能关系

禁止依据：

* Commit 数量
* 新增行数
* 删除行数
* 文件数量
* 单次提交大小

建议采用两层策略：

```text
确定性规则预聚合
    ↓
AI 语义聚合
    ↓
结果校验
```

确定性规则可以先根据：

* 相同仓库
* 相同 Scope
* 接近时间
* 文件目录重合
* Commit Type 关联

* 不应让整个周报功能完全不可用
* 清楚标记为“规则聚合结果”

# 十八、可信度计算

实现：

```text
src/gitpulse/weekly/confidence.py
```

可信度等级：

```text
high
medium
low
```

默认规则：

## High

满足至少一种：

* Commit Hash 直接支持内容
* CommitRecord 已由用户确认
* Worklog 由用户手动创建并确认
* 用户明确提供风险或计划
* 内容可以直接从来源文本中证明

## Medium

情况包括：

* 多个 Commit 的合理归纳
* 同一主题下的语义合并
* 将技术动作归纳为清晰成果
* 来源明确，但标题或总结为 AI 概括

## Low

情况包括：

* 推断业务目标
* 推断测试已经完成
* 推断性能提升
* 推断工作价值
* 推断下周计划
* 缺少直接来源
* 来源之间存在冲突

处理规则：

```text
high：
默认可进入草稿和正式周报。

medium：
进入草稿，但需要用户确认。

low：
默认不进入正式周报，放入 needs_confirmation。
```

配置：

```yaml
weekly:
  exclude_low_confidence: true
  require_medium_confirmation: true
```

用户确认后：

* Medium 可转换为确认内容
* Low 可以保留原始 Confidence，但标记用户已确认
* 或将最终可信状态记录为 `user_confirmed`
* 不应伪装成原始 High

建议增加：

```python
evidence_confidence: str
user_confirmed: bool
```

避免混淆证据可信度和用户确认状态。

# 二十七、Source Coverage

计算：

```text

÷
```

本阶段不使用：

```text

  ↓
pending_confirmation
  ↓
confirmed
  ↓
```

```text

confirmed → archived
```

禁止：


# 三十五、未提交变更

参数：

```bash
gitpulse weekly --include-uncommitted
```

规则：

1. 读取当前未提交 Diff。
2. 执行过滤、截断和安全扫描。
3. 使用 Commit Generator 的摘要能力，或规则摘要。
4. 标记来源类型为 `uncommitted`。
5. 默认 Confidence 为 Medium 或 Low。
6. 必须用户确认后才能进入完成事项。
7. 更适合进入“进行中”或“待处理”，但原始模板没有进行中章节。
8. MVP 可以放入 `needs_confirmation`。
9. 不得把未提交代码描述为已经完成或已发布。
10. 不得保存完整 Diff。

提示：

```text
检测到未提交变更。

请确认是否加入周报草稿。
```

# 四十四、周报事实冲突

可能出现：

* Commit 表示功能完成
* Worklog 表示仍在验证
* 用户风险表示尚未完成
* 多个记录描述不同结果

处理规则：

1. 不自动选择更乐观结论。
2. 优先保留可直接验证的技术事实。
3. 将冲突内容放入 `needs_confirmation`。
4. 告知用户冲突来源。
5. 不允许 AI 静默消解冲突。
6. 用户确认后保存最终选择。
7. 保留冲突审计信息。

示例：

```text
发现内容冲突：

来源一：
commit:a13f2bc
“完成设备自动重连处理”

来源二：
worklog:worklog_001
“自动重连仍需进一步验证”

请选择最终描述。
```

* 用户风险
* 用户计划
* AI 生成周报
