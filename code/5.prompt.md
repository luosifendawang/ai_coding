# 一、本阶段目标

本阶段负责把 GitPulse 生成的开发工作数据持久化，并提供完整的手动工作记录能力。

需要实现以下闭环：

```text
用户生成 Commit Message
    ↓
用户选择或编辑候选结果
    ↓
用户确认最终 Commit Message
    ↓
保存结构化 Commit 工作记录
    ↓
保存来源文件、风险和生成信息
    ↓
用户添加非代码 Worklog
    ↓
支持查询、编辑和删除 Worklog
    ↓
支持查看历史 Commit 记录
    ↓
为后续周报聚合提供数据
```

本阶段必须完成：

1. SQLite 数据库初始化
2. SQLAlchemy ORM 模型
3. Repository 数据访问层
4. 数据库事务管理
5. 数据库版本与迁移机制
6. Repository 仓库信息保存
7. Commit 结构化记录保存
8. 风险记录保存
9. Worklog 增删改查
10. 历史记录查询
11. Commit 用户确认流程
12. `gitpulse worklog` 命令

14. 数据导出基础能力
15. 数据删除与隐私控制

# 四、存储设计原则

必须遵循：

1. MVP 使用本地 SQLite。
2. 数据默认只保存在用户本地。
3. 业务层不得直接执行 SQL。
4. 所有数据库访问通过 Repository。
5. 多步写入必须使用事务。
6. 数据库错误不得破坏 Git 仓库状态。
7. 数据库错误不得导致 Commit 自动执行。
8. 原始完整 Diff 默认不得写入数据库。
9. 原始敏感值不得写入数据库。
10. API Key、Webhook 和 Secret 不得写入数据库。
11. 保存的文件路径应优先使用仓库相对路径。
12. 本地绝对路径应谨慎保存并避免输出到远程。
13. 删除操作必须经过用户确认。
14. 数据导出前应执行必要的敏感信息检查。
15. 时间统一保存为带时区的 ISO 8601 字符串或 UTC 时间。
16. SQLite 连接应启用外键约束。
17. 测试数据库必须与用户真实数据库隔离。
18. 数据库文件不存在时自动创建。
19. 数据库版本需要可追踪。
20. 不得因数据库损坏而静默丢弃用户数据。

# 五、Storage 配置

完善 `.gitpulse.yml`：

```yaml
storage:
  database: ~/.gitpulse/data.db
  report_dir: ./reports
  auto_initialize: true
  enable_history: true
  store_file_list: true
  store_diff_summary: true
  store_raw_diff: false
  retention_days: null
  sqlite_timeout_seconds: 10
```

建议配置模型：

```python
from pathlib import Path
from pydantic import BaseModel, field_validator


class StorageConfig(BaseModel):
    database: Path = Path("~/.gitpulse/data.db")
    report_dir: Path = Path("./reports")
    auto_initialize: bool = True
    enable_history: bool = True
    store_file_list: bool = True
    store_diff_summary: bool = True
    store_raw_diff: bool = False
    retention_days: int | None = None
    sqlite_timeout_seconds: float = 10.0

    @field_validator("retention_days")
    @classmethod
    def validate_retention_days(
        cls,
        value: int | None,
    ) -> int | None:
        if value is not None and value <= 0:
            raise ValueError("retention_days 必须大于 0")
        return value
```

要求：

* `~` 必须正确展开
* 相对路径需要明确相对于项目目录还是当前目录
* 推荐数据库路径相对于用户目录解析
* 报告目录可以相对于仓库根目录解析
* `sqlite_timeout_seconds` 必须大于 0
* 默认不保存原始 Diff
* 即使用户配置 `store_raw_diff=true`，也必须保存脱敏后的 Diff
* 不允许保存第三阶段发现的原始敏感值
* 配置目录不存在时自动创建
* 创建目录失败时给出友好错误

# 七、ORM Base 和通用字段

在 `orm_models.py` 中定义：

```python
from sqlalchemy.orm import DeclarativeBase


class Base(DeclarativeBase):
    pass
```

可以定义通用时间字段 Mixin：

```python
class TimestampMixin:
    created_at: Mapped[datetime]
    updated_at: Mapped[datetime]
```

注意：

* SQLite 对时区支持有限
* 建议统一保存 UTC
* 业务层转换为本地时区显示
* 时间字段不得使用无时区的本地当前时间
* 测试中应可以注入固定时钟
* 避免直接在大量代码中调用 `datetime.now()`

建议实现：

```python
def utc_now() -> datetime:
    return datetime.now(timezone.utc)
```

## 1. repositories

```sql
CREATE TABLE repositories (
    id TEXT PRIMARY KEY,
    name TEXT NOT NULL,
    root_path TEXT NOT NULL,
    remote_url TEXT,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);
```

建议扩展字段：

```text
current_branch
git_user_name
git_user_email
last_seen_at
```

但不要将频繁变化的当前分支当作仓库永久属性。

推荐 ORM：

```python
class RepositoryORM(Base, TimestampMixin):
    __tablename__ = "repositories"

    id: Mapped[str] = mapped_column(String, primary_key=True)
    name: Mapped[str] = mapped_column(String, nullable=False)
    root_path: Mapped[str] = mapped_column(String, nullable=False)
    remote_url: Mapped[str | None] = mapped_column(String, nullable=True)
    created_at: Mapped[datetime] = mapped_column(...)
    updated_at: Mapped[datetime] = mapped_column(...)
```

要求：

* 同一仓库重复初始化时不得重复创建
* 仓库 ID 应稳定
* 不要只使用仓库名称作为唯一标识
* 推荐基于规范化 root path 和 remote URL 生成稳定 ID
* Root Path 需要规范化
* 大小写敏感策略应考虑 Windows
* Remote URL 不得包含嵌入式密码或 Token
* 如果 URL 包含凭证，保存前必须清除

## 2. commit_records

基础表结构：

```sql
CREATE TABLE commit_records (
    id TEXT PRIMARY KEY,
    repository_id TEXT NOT NULL,
    commit_hash TEXT,
    branch TEXT,
    commit_type TEXT,
    scope TEXT,
    subject TEXT NOT NULL,
    body TEXT,
    summary TEXT,
    files_json TEXT,
    insertions INTEGER DEFAULT 0,
    deletions INTEGER DEFAULT 0,
    confidence TEXT,
    confirmed_by_user INTEGER DEFAULT 0,
    created_at TEXT NOT NULL,
    FOREIGN KEY(repository_id) REFERENCES repositories(id)
);
```

建议扩展：

```text
source_type
generation_provider
generation_model
should_split
split_confidence
selected_candidate
user_context
security_summary_json
verification_json
updated_at
```

推荐 ORM：

```python
class CommitRecordORM(Base, TimestampMixin):
    __tablename__ = "commit_records"

    id: Mapped[str] = mapped_column(String, primary_key=True)
    repository_id: Mapped[str] = mapped_column(
        ForeignKey("repositories.id"),
        nullable=False,
        index=True,
    )
    commit_hash: Mapped[str | None] = mapped_column(
        String,
        nullable=True,
        index=True,
    )
    branch: Mapped[str | None] = mapped_column(String)
    commit_type: Mapped[str | None] = mapped_column(String)
    scope: Mapped[str | None] = mapped_column(String)
    subject: Mapped[str] = mapped_column(Text, nullable=False)
    body: Mapped[str | None] = mapped_column(Text)
    summary: Mapped[str | None] = mapped_column(Text)
    files_json: Mapped[str | None] = mapped_column(Text)
    insertions: Mapped[int] = mapped_column(Integer, default=0)
    deletions: Mapped[int] = mapped_column(Integer, default=0)
    confidence: Mapped[str | None] = mapped_column(String)
    confirmed_by_user: Mapped[bool] = mapped_column(Boolean, default=False)
    source_type: Mapped[str] = mapped_column(
        String,
        default="generated_commit",
    )
    generation_provider: Mapped[str | None] = mapped_column(String)
    generation_model: Mapped[str | None] = mapped_column(String)
    selected_candidate: Mapped[str | None] = mapped_column(String)
    should_split: Mapped[bool] = mapped_column(Boolean, default=False)
    split_confidence: Mapped[float | None] = mapped_column(Float)
    verification_json: Mapped[str | None] = mapped_column(Text)
    security_summary_json: Mapped[str | None] = mapped_column(Text)
```

要求：

* `subject` 必须保存用户最终确认版本
* 不保存未选择的候选，除非明确设计候选审计表
* 如果保存候选，应保证不包含敏感信息
* `body` 可保存为 JSON 或 Markdown 文本
* 推荐 JSON 数据统一通过序列化器处理
* 不直接 `json.dumps()` 散落在业务代码中
* 不允许重复保存相同 Commit Hash 的确认记录
* 未执行真实 Git Commit 时 `commit_hash` 可以为空
* 后续发现 Hash 时应支持补充更新
* `confirmed_by_user=false` 的记录不得进入正式周报
* 被建议拆分但用户仍确认整体提交时，需要保留相关标记
* 数据库不负责执行 Git Commit

# 十、ID 生成策略

所有记录使用稳定、可读但不泄露敏感信息的 ID。

示例：

```text

推荐：

* 使用 UUID4
* 或 ULID
* 或时间前缀加随机字符串

要求：

2. ID 不包含用户名。
3. ID 不包含邮箱。
4. ID 不包含仓库绝对路径。
5. ID 不包含 Commit Message。

        ...

        ...
```

Commit 记录保存流程：

```text
开始事务
    ↓
Upsert Repository
    ↓
创建 CommitRecord
    ↓
创建 Risk 记录
    ↓
全部成功
    ↓
Commit 事务
```

任何一步失败：

```text
Rollback 全部数据
```

不得出现：

* CommitRecord 已保存
* Risk 保存失败
* 数据库留下半完成记录

# 十四、数据库迁移

MVP 不一定需要完整 Alembic，但必须有最小迁移机制。

推荐方案之一：

## 方案 A：Alembic

优点：

* 成熟
* 可扩展
* 支持版本迁移

缺点：

* 项目复杂度较高

## 方案 B：自定义顺序迁移

例如：

```python
MIGRATIONS = [
    Migration(
        version=1,
        name="initial_schema",
        upgrade=upgrade_v1,
    ),
]
```

第三方依赖较少，适合 MVP。

无论采用哪种方案，必须满足：

1. 新数据库可以初始化到最新版本。
2. 已有数据库可以读取当前版本。
3. 已执行迁移不得重复执行。
4. 迁移必须在事务中执行。
5. 迁移失败后不得标记为成功。
6. 不得静默删除旧数据。
7. 数据库版本高于当前应用支持版本时，应拒绝启动。
8. 迁移前可以创建备份提示。
9. 测试至少覆盖 V0 到 V1。
10. 未来表结构变更有明确扩展路径。

# 十六、Commit 结构化记录保存

第四阶段的 `gitpulse commit` 只生成结果。

第五阶段增加用户确认和保存能力。

建议流程：

```text
生成三个 Commit Message 候选
    ↓
用户选择候选
    ↓
用户可编辑 Subject 和 Body
    ↓
展示最终预览
    ↓
用户确认保存
    ↓
保存 CommitRecord 和 Risk
```

注意：

“保存”是保存 GitPulse 工作记录，不是执行 Git Commit。

必须明确提示：

```text
GitPulse 只会保存工作记录，不会执行 git commit。
```

---

## 保存条件

只有满足以下条件才能保存为确认记录：

1. 用户明确选择候选或完成编辑。
2. 最终 Subject 通过格式验证。
3. 安全扫描已经完成。
4. 最终内容中不包含完整敏感信息。
5. 用户明确确认保存。
6. 数据库初始化成功。

---

## 记录内容

从现有结果中保存：

```text
repository_id
branch
commit_hash
commit_type
scope
subject
body
summary
files
insertions
deletions
confidence
selected_candidate
should_split
split_confidence
provider_name
model_name
security_summary
verification
confirmed_by_user
```

如果当前尚未执行真实 Commit：

```text
commit_hash = null
source_type = generated_commit
```

后续可以通过命令补充 Hash：

```bash
gitpulse history link-commit <record-id> <commit-hash>
```

该命令可以作为本阶段可选功能。

# 二十七、Worklog 敏感信息检查

Worklog 不包含代码 Diff，但仍可能包含：

* API Key
* Token
* 密码
* 内网地址
* 邮箱
* 手机号
* 身份证号

建议在保存前调用第三阶段的安全扫描能力。

处理规则：

* critical/high Secret：阻止保存或要求用户修改
* medium 隐私信息：提示用户确认
* low 信息：可保存但提示
* 数据库存储中不得保存原始凭证

如果自动脱敏：

```text
检测到疑似敏感信息：

结果字段：
包含疑似 Access Token

该内容不能直接保存。

请移除敏感值后重试。
```

不建议对 Worklog 中的高风险 Secret 自动静默替换，因为用户可能误以为原文已保存。

# 三十、Commit Hash 关联

用户生成并保存 Commit Message 后，可能稍后手动执行：

```bash
git commit
```

本阶段可以实现可选关联命令：

```bash
gitpulse history link-commit <record-id> <commit-hash>
```

校验：

1. Commit Hash 在当前仓库存在。
2. 记录属于当前仓库。
3. 该记录尚未关联其他 Hash，或用户明确确认覆盖。
4. Commit Message 与记录是否大致一致可以作为提示。
5. 不要求完全匹配。
6. 不自动修改 Git 历史。
7. 不自动 Amend。

也可以实现：

```bash
gitpulse history link-latest <record-id>
```

将当前 HEAD 关联到记录，但必须用户确认。

该功能如果超出本阶段时间，可以预留 Service 接口，不强制实现 CLI。
